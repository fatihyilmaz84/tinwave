blocking findings:
- crates/tinwave-playback/src/decoder.rs:777-790 — a rate flush waits for its ack at 1 ms with no cap. Nothing bounds this while the stream is not running. Scenario: `switch_device` fails (engine.rs:643 restarts the decoder "into a ring nobody plays", then OutputLost). The new mark makes `audible()` true, so the next `set_rate` starts an Audible flush that is never acked. The decoder then polls until the user runs another command. I measured it with an instrumented scratch copy (failed switch, then `set_rate(1.25)`): 133 and then 130 rate-ack polls per 2 s, and it never stops. That is about 65/s here, limited by the 15.6 ms timer; on 1 ms timers it is 1000/s. The old backoff gave about 20/s. The same happens if the device dies before the host switches. This breaks what FLUSH_WAIT_MIN's own doc promises (decoder.rs:155-158: "failed device switch ... about 20 wakeups per second instead of 1000"), and the engine's choice that `poll_soon` is false once the output is lost so nothing keeps the host awake. Fix: poll at FLUSH_WAIT_MIN for a bounded window (e.g. 20–50 ms, or N polls), then fall back to the normal backoff up to FLUSH_WAIT_MAX. Add a unit test on `wait_for_ack` showing the cap.
- crates/tinwave-playback/tests/rate.rs:235-266 (`Rec::change_rate`), driven by the 40-restart `no_click_at_a_rate_step_...` — the pacing loop counts iterations: 4-frame callbacks with a `sleep(200 µs)` between them, at least 60 callbacks per fade, 40 restarts, a 5/6 s pre-buffer each. Under CPU load each sleep lasts a scheduler quantum, so the binary goes from main's ~4 s to ~25 s; under nextest it took 83 s (SLOW). The ticket asked for faster, load-independent tests, and the T-0066 failures were under exactly this load. Fix: make the slow pacing apply only to the fade window (e.g. render bigger blocks until the request is visible, then small ones), or use fewer restarts with chosen phases. Measure against main's rate binary under the same load and report both numbers.

non-blocking findings:
- crates/tinwave-playback/tests/rate.rs:5-11 — the header says nothing "reads a clock for an assertion", but `a_drag_costs_one_flush_per_interval_...` bounds flushes by `Instant` elapsed time. Because of that bound, a disabled throttle is only caught on a fairly idle machine: under load, elapsed time widens the bound past the 13 flushes the mutation produced. This is inherent to the hybrid clock; T-0076 removes it.
- The hybrid throttle clock (lead Q1) is correct. `throttle_wait` returns min(monotonic, injected), which never exceeds the monotonic remainder of 125 ms. Every wait in the loop is capped by `rate_wait` (decoder.rs:382, 399); the parked and awaiting branches never have a deferred change. In production a forward wall-clock jump costs at most one early flush, and a backward jump changes nothing (decoder.rs:757-764, unit-tested).
- Excluding `starved` restarts cannot hide a too-short fade. The flag needs the ring to pass through 1..600 frames before the restart. After the 40,000-frame pre-buffer that means the decoder did not answer for about 2 s, and at least half the restarts must stay in. A systematic fade regression therefore shows in the restarts that remain (0 of 40 were starved in all my runs).
- decoder.rs:713 — a device switch (`Reconfigure` -> `restart`) clears `reported`. A device switch that re-reads a broken track still reports a second TrackFailed. That is outside this ticket's wording, but it is the same listener-facing duplicate.
- After a park (exclusive mode), `heard` is already None when `resume` reopens the item (decoder.rs:845-847). A file that vanishes between the park and the resume would leave as Finished. This is very unlikely: same-rate reopens do not park.
- RT check: renderer.rs is not touched and the new HashSet work runs on the decoder thread only. rt_alloc passed in the 802 run. Scope: only decoder.rs and tests/rate.rs changed, no work/ edits.
