blocking findings:
- crates/tinwave-playback/src/controller/runtime.rs:80 + runtime.rs:191 + mod.rs:327 — Shutting down the app now waits for the decoder thread. The engine's own docs (engine.rs:68-71) promise the opposite: dropping it does not wait, so a stuck read can never hang application exit. Here, `ControllerHandle::drop`/`shutdown` joins the controller thread, which runs `Controller::shutdown` → `Engine::shutdown` → `thread.join()` on the decoder. `ControllerHandle` is documented as "what the app holds", so this is the production exit path. Failure scenario: the library is on a NAS or SMB share that drops while a track is opening or reading, so the decoder sits in `File::read`/`CreateFile` for tens of seconds. The user quits, the UI thread drops the handle, and the app hangs until the OS gives up on the read. Suggested fix: in the controller thread, still stop, drain and `mapper.finish` (so SessionEnded is emitted), then drop the `Engine` instead of calling `Engine::shutdown`. One way is a non-joining `Controller::close()`; keep the joining `shutdown()` for tests. Add a test where a `SourceOpener` blocks forever and `ControllerHandle::drop` still returns.
- crates/tinwave-playback/src/controller/mapper.rs:192-202 (with `send`, mapper.rs:569-579) — A repeat-mode change made while there is no session is silently lost, and it can never be reported later. `set_repeat` updates `self.repeat` and then calls `send`, which does nothing outside a session. Concrete case: the user opens the app and turns on repeat-one before pressing play, or toggles it after a pause longer than 30 minutes. No `RepeatModeChanged` is ever emitted, yet `status().repeat` is `One`, so the change is never recorded. This breaks the hard rule that every interaction expressing a preference emits a signal. Unlike the volume case ("Gestures need a session", mod.rs:67-68), it is also not documented. Suggested fix: keep a "reported" repeat mode next to the current one, and when `ensure_session` opens the next session, emit `RepeatModeChanged` right after `SessionStarted` if they differ. Add a test: set repeat-one with nothing loaded, play, and expect SessionStarted, RepeatModeChanged(One), PlayStarted.

non-blocking findings:
- crates/tinwave-playback/src/controller/mod.rs:185-187 — `Controller::load` polls, then `Engine::load` polls again inside itself (engine.rs:196), and the events from that second poll are mapped after `mapper.set_queue` has replaced the table. If a gapless advance lands between the two polls and the advanced-to item is not in the new queue, mapper.rs:330-335 logs at `error` and that play gets no PlayStarted and no outcome. The result stays consistent, but this is a benign race being logged as an error. Fix: keep the old entries in the table until the drain finishes (merge, then prune), or log it at debug.
- crates/tinwave-playback/src/controller/mapper.rs:464-466 — A seek on a play whose session has expired (paused 30 minutes or more, then seeked, then resumed) is dropped. Unlike volume, this is not documented. Either document it with the volume rule or open or defer the gesture.
- crates/tinwave-playback/src/controller/mapper.rs:529-538 — A mode change in `OutputReopened` while there is no session updates `self.mode` without emitting, so that `ExclusiveModeToggled` is lost for good. This has the same root cause as the repeat finding and the same fix.
- crates/tinwave-playback/src/controller/mod.rs:16-17 and runtime.rs:43-45 — The docs say commands block the caller "only for the microseconds". `switch_device` opens the output synchronously (engine.rs:450-452), which can take 100 ms or more (Bluetooth or exclusive WASAPI), and `ControllerHandle::call` waits with no timeout. The doc should say so; the shell should call `switch_device` off the UI thread.
- crates/tinwave-playback/src/controller/types.rs:104-112 — `TimezoneSource::local_offset`/`session_started` run on the controller thread, inside a drain. Document that implementations must not block (no DB lock or writer call that waits), or playback control stalls.
- docs/guides/signal-catalog.md §2/§8 (not in this ticket's scope) — After the 1b amendment, a play's Completed or Skipped can land in a later session than its PlayStarted. The future live play-record writer (database.md:127) must pair a play start with its outcome per device, not per session. The catalog should state this rule.
