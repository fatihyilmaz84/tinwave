blocking findings:
- crates/tinwave-db/src/wipe.rs:217-259 (`rewrite_keys`) — The wipe runs one full-table-scan `UPDATE ... WHERE context_key = ?` for each distinct stored key. `play.context_key` has no index (migrations/signals/0001_init.sql:62 has only `play_rec_ts`). So the wipe holds the IMMEDIATE write lock for O(distinct keys × rows), and the doc claim "a handful of statements" is false. A key combines 7 fields, and the project's own growth sim (tests/growth/sim.rs:1084) makes keys from a space of tens of thousands, at about 60 snapshots a day.
  - **Measured with the real `SignalWiper`.** I ran a scratch test on the merged tree in release mode: 131,400 plays (reference listener, 120 a day for 3 years), wiping NetworkPlace. With 300 distinct keys the wipe took 2.85 s. With 1,500 distinct keys it took 16.3 s. A second connection doing `BEGIN IMMEDIATE` with the writer's 5 s busy timeout failed with "database is locked" after 5.5 s.
  - **Effect.** During a user wipe, `SignalWriter` batches fail with SQLITE_BUSY. The writer then stops draining the bus and retries every 2 s, so low-priority events can be dropped by the bus and play-end flushes are delayed. The wipe call also blocks whatever thread calls it for tens of seconds.
  - **Suggested fix.** Rewrite each table in one scan. One way: a single `UPDATE {table} SET {col} = CASE WHEN ({col} & :keep) & 0xFFFFFF = 0 THEN 0 ELSE {col} & :keep END WHERE {col} BETWEEN 1 AND 4294967295 AND ({col} & :clear) != 0`, preceded by a `SELECT EXISTS(... {col} < 0 OR {col} > 4294967295)` check that keeps the OutOfRange rollback. The same SQL pattern took 0.21 s on 131k rows in my Python reproduction. Another way: fill a temp old→new map table and run one `UPDATE ... FROM`.
  - **Tests to add.** A test that pins the semantics against `ContextKey::clear_raw` (for example, the existing tests plus a randomized many-keys case). A test that a `SignalStore::write_batch` issued while a wipe of a reference-size table is running succeeds within the busy timeout.

non-blocking findings:
- crates/tinwave-db/src/wipe.rs:153-158 — There is no test that drives the wiper and `SignalStore`/`SignalWriter` concurrently. On the race you asked about, I find no reintroduction through the writer today. `play.context_key` is resolved from `context_snapshot.key` inside the writer's own IMMEDIATE transaction (play.rs:359-382), so a play row committed after the wipe reads the already-cleared snapshot key. This holds even for a play whose PlayStarted came before the wipe. The remaining risk is the future snapshot producer: a snapshot row built from pre-wipe values and inserted after the wipe would carry the wiped fields.
- crates/tinwave-db/src/wipe.rs:39-43 — `context_snapshot.hash` (UNIQUE, a hash of the quantized fields) is also derived from the wiped values. After a wipe the row's `key` no longer matches its `hash` and `fields`. If the context hub ever dedupes against the DB by hash, it would reuse a row whose key was wiped. This belongs with the parked `fields` blob work.

A T1 tier wipe does clear activity, through Clock. A future Signal Center that offers a per-category wipe of idle, power or fullscreen must add them to `derived_fields`. Otherwise the ownership table matches context-engine.md, signal-catalog §7 tiers and the lead's ruling: holidays are folded into Clock (T1), daypart is clock-based, and Calendar and T0 have no field.
